# Шаг 1 — Фундамент: Koin, Voyager, Room и MVI

## Цель и принятые решения

Подготовить инфраструктуру для следующих шагов: общий DI-граф, три таба с независимой навигацией, рабочая БД на Android и iOS и понятный шаблон разработки фич.

Документ для сохранения: `docs/STEP_1_FOUNDATION.md`.

С учётом уточнений:
- В Room сразу создаём **Deck + Flashcard** со связью между ними.
- Пользовательский CRUD, репозитории и use cases остаются шагам 2–3.
- Используем **AndroidX KMP ViewModel** и экспериментальную поддержку lifecycle в Voyager.
- MVI описываем как соглашение с примером, без обязательного базового класса.

## Task list

### 1.1. Подготовить зависимости и проверить совместимость

- [ ] Зафиксировать исходное состояние: Android собирается, iOS-приложение запускается.
- [ ] Добавить в version catalog Koin, Voyager, Room, SQLite Bundled, KSP и coroutines.
- [ ] Для Voyager подключить navigator, tab navigator и lifecycle KMP одной версии.
- [ ] Проверить совместимость выбранных версий с текущими Kotlin `2.4.21`, AGP `9.1.1` и Compose Multiplatform `1.12.2`.
- [ ] Зафиксировать конкретные версии без динамических диапазонов; экспериментальность Voyager lifecycle отметить в документе.
- [ ] Проверить разрешение зависимостей для Android, `iosArm64` и `iosSimulatorArm64`.

**Готово, когда:** зависимости разрешаются на всех существующих таргетах без изменения выбранного стека.

### 1.2. Создать core-модули

- [ ] Добавить `core:common`, `core:domain`, `core:data` в Gradle settings.
- [ ] Настроить Android и оба iOS-таргета по существующему образцу KMP-модулей проекта.
- [ ] Подключить зависимости:
  - `core:domain → core:common`;
  - `core:data → core:domain + core:common`;
  - `shared → новые core-модули`.
- [ ] В `core:common` добавить внедряемый `AppDispatchers` с `Main`, `IO`, `Default` и источник текущего времени.
- [ ] В `core:domain` зафиксировать правила: отсутствие Compose, Room, Koin и платформенных API.
- [ ] Не добавлять заранее пустые интерфейсы репозиториев и use cases: их контракты определить вместе с CRUD.

**Готово, когда:** модули компилируются на обеих платформах, зависимости не образуют циклов.

### 1.3. Настроить Room KMP

- [ ] В `core:data` подключить Room runtime, compiler через KSP и Bundled SQLite.
- [ ] Настроить KSP отдельно для Android и обоих iOS-таргетов.
- [ ] Создать `RepetrailDatabase`, версия схемы — `1`.
- [ ] Настроить генерацию конструктора БД через `RoomDatabaseConstructor`.
- [ ] Включить экспорт схем и хранение JSON-схем в Git.

Схема первой версии:

| Entity | Поля |
|---|---|
| `DeckEntity` | `id: Long`, `name: String`, `description: String?`, `createdAt: Long`, `updatedAt: Long` |
| `FlashcardEntity` | `id: Long`, `deckId: Long`, `term: String`, `definition: String`, `example: String?`, `createdAt: Long` |

- [ ] Для обеих таблиц использовать автоматически генерируемый первичный ключ.
- [ ] Добавить внешний ключ `Flashcard.deckId → Deck.id`, индекс по `deckId` и каскадное удаление карточек.
- [ ] Хранить timestamps в миллисекундах Unix.
- [ ] Создать минимальные DAO: вставка, чтение по ID, наблюдение списка через `Flow`, удаление.
- [ ] Реализовать Android builder с application context и постоянным путём БД.
- [ ] Реализовать iOS builder с постоянным путём внутри sandbox приложения.
- [ ] Общую конфигурацию выполнять в `commonMain`: Bundled SQLite и coroutine context для запросов. Основа — [официальная схема настройки Room KMP](https://developer.android.com/kotlin/multiplatform/room).
- [ ] Не заполнять пользовательскую БД тестовыми данными при запуске.
- [ ] Не включать destructive migration.

**Готово, когда:** на Android и iOS можно записать колоду с карточкой и прочитать их после закрытия и повторного открытия БД.

**Миграции:** предыдущей схемы пока нет. На шаге 1 создаём и сохраняем v1; реальную миграцию добавляем при первом изменении схемы, без искусственной версии v2.

### 1.4. Собрать DI-граф

- [ ] Создать общий `initKoin` в `shared`, принимающий платформенную конфигурацию.
- [ ] Разделить регистрацию на common-, data- и platform-модули.
- [ ] Зарегистрировать dispatchers, источник времени, database builder, singleton БД и DAO.
- [ ] Запускать Koin на Android из `Application` до создания UI.
- [ ] Инициализировать Koin на iOS до создания общего Compose UI.
- [ ] Исключить повторную инициализацию при пересоздании Activity или UIViewController.
- [ ] Сохранить работу previews без запуска production DI-графа.
- [ ] Проверить реальное получение БД и DAO из контейнера на обеих платформах: одного успешного `startKoin` недостаточно.

**Готово, когда:** весь зарегистрированный граф разрешается без ошибок, БД создаётся один раз на контейнер.

### 1.5. Перевести табы на Voyager

- [ ] Заменить `remember(selectedTab)` и `when(selectedTab)` на `TabNavigator` и `CurrentTab`.
- [ ] Создать табы Tasks, Cards, Menu; начальный таб — Tasks.
- [ ] Сохранить текущие экраны, тему, floating navigation bar и обработку insets.
- [ ] Создать отдельный вложенный `Navigator` внутри каждого таба — по [схеме Voyager](https://voyager.adriel.cafe/navigation/tab-navigation/).
- [ ] Использовать стабильные ключи экранов и навигаторов.
- [ ] Для проверки вложенной навигации добавить простой экран «О приложении», доступный из Menu.
- [ ] Сохранять стек и UI-состояние таба при переключении.
- [ ] Повторное нажатие выбранного таба не должно сбрасывать его стек.
- [ ] Android Back сначала закрывает вложенный экран; на корне остаётся стандартное поведение Activity.
- [ ] На iOS добавить явную кнопку возврата на вложенном экране.
- [ ] Проверить сценарий: Menu → О приложении → Cards → Menu — открыт прежний вложенный экран.

**Готово, когда:** три таба и вложенные переходы работают на Android и iOS без дублирования экранов.

### 1.6. Зафиксировать MVI и lifecycle ViewModel

- [ ] Описать контракт фичи: immutable `State`, `Intent`, `SideEffect`, `ViewModel`.
- [ ] Зафиксировать интерфейс ViewModel: `StateFlow<State>`, `Flow<SideEffect>`, `onIntent(intent)`.
- [ ] Использовать приватный `MutableStateFlow` и публичный read-only state.
- [ ] Для одноразовых эффектов использовать `Channel` с получением через `receiveAsFlow`; эффекты не хранить в State.
- [ ] Зафиксировать: UI передаёт intents, ViewModel выполняет операции в `viewModelScope`, UI обрабатывает навигационные эффекты.
- [ ] Описать обработку загрузки, ошибки и повторной попытки; отмену корутин не превращать в пользовательскую ошибку.
- [ ] Привязать ViewModel к экрану Voyager, а не к singleton приложения.
- [ ] Подключить lifecycle KMP provider над навигаторами согласно [документации Voyager](https://voyager.adriel.cafe/android-viewmodel/viewmodel-kmp/).
- [ ] Добавить пример контракта и получения ViewModel через Koin в этот документ.
- [ ] В тестовом harness проверить: recomposition и переключение табов сохраняют экземпляр, окончательный `pop` освобождает ViewModel и её корутины.

**Готово, когда:** следующую фичу можно реализовать по документированному образцу без выбора нового архитектурного подхода.

## Проверка и критерии завершения

- [ ] Android-приложение собирается и запускается.
- [ ] iOS framework компилируется для устройства и симулятора; приложение запускается в симуляторе.
- [ ] DI-тесты разрешают все зарегистрированные зависимости на обеих платформах.
- [ ] Room-тесты проверяют запись/чтение, сохранность после переоткрытия, внешний ключ и каскадное удаление.
- [ ] MVI-тест проверяет изменение State и однократную доставку SideEffect.
- [ ] Проверены независимые стеки табов, возврат назад и lifecycle ViewModel.
- [ ] На Android после поворота сохраняются выбранный таб и вложенный экран.
- [ ] После перезапуска процесса приложение открывается на Tasks, данные Room сохраняются.
- [ ] В документе записаны фактически выполненные команды и результаты проверок.
- [ ] В `MASTER_PLAN.md` отмечены выполненные критерии шага 1 и уточнено, что схема Deck + Flashcard подготовлена заранее.

## Границы шага

CRUD-интерфейсы, репозитории, бизнес-модели, уроки и Leitner реализуются на следующих шагах. Демо-контент существующих экранов пока сохраняется. Шаблонный `feature:add_card` на этом шаге не перерабатывается.

Порядок выполнения: **зависимости → модули → Room → DI → навигация → MVI/lifecycle → итоговая проверка**.
